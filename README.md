# VPS-WARP

**Cloudflare WARP на вашем VPS без официального клиента.**  
Нативный WireGuard + умный watchdog с авто-ротацией endpoint. Сделан для работы с Xray-core, Remnawave, 3X-UI и Marzban.

---

## Зачем

Хостинги блокируют, Cloudflare шейпит трафик из датацентров — WARP перестаёт работать. Стандартный `warp-cli` жирный и капризный.

VPS-WARP поднимает туннель через `wg-quick` и ставит systemd-watchdog, который каждые 3 минуты пингует `1.1.1.1`, `8.8.8.8` и `9.9.9.9` через туннель. Если пинг не проходит или хэндшейк не обновлялся больше 3 минут — скрипт меняет endpoint на случайный из пула Cloudflare и перезапускает туннель. Тихо, без вашего участия.

---

## Особенности

- **Нативный WireGuard** — никаких проприетарных демонов Cloudflare
- **Авто-ротация endpoint** — при падении связи выбирает случайный адрес из `188.114.{96,97}.x` на портах `2408 / 500 / 4500 / 1701`. Локальный порт при этом не меняется
- **Закреплённый `ListenPort`** — Cloudflare выбирает машину выхода по паре «наш адрес:порт → endpoint:порт», то есть пара определяет адрес и страну выхода. Порт выбирается один раз, при первой установке, и дальше не меняется — ни ротацией, ни переустановкой, ни `vps-warp update`. Поэтому ключ к выходу — endpoint: тот же endpoint — тот же выход, новый — новый жребий (см. [Закреплённый ListenPort](#закреплённый-listenport))
- **Страна выхода как у сервера** — часть машин Cloudflare выходит с адресов, которые он сам относит к другой стране. Скрипт сверяет страну выхода при установке и на каждом прогоне watchdog и при несовпадении меняет endpoint на живом интерфейсе. Выключается флагом `--no-egress-check` (см. [Страна выхода](#страна-выхода))
- **Изолированная маршрутизация** — `Table = 51820` + правило `ip rule fwmark 255`. Основной трафик сервера не затрагивается: в туннель уходит только то, что помечено меткой 255 (см. [Интеграция с Xray](#интеграция-с-xray))
- **TCP MSS Clamping** — правило в `mangle POSTROUTING` на исходящих через `warp`, MSS 1240 при MTU 1280. Предотвращает зависания на тяжёлых сайтах
- **Backoff при ротации** — если Cloudflare заблокирован целиком, watchdog не дёргает туннель каждые 3 минуты, а наращивает паузу до 30 минут
- **rp_filter** — при строгом режиме (`=1`, дефолт RHEL/Rocky/Alma) обратный трафик туннеля дропается ядром. Скрипт понижает до loose (`=2`) и закрепляет в `/etc/sysctl.d/99-vps-warp.conf`. На Ubuntu, где уже `=2`, ничего не трогает
- **Только IPv4** — IPv6-адреса и маршруты вырезаются из конфига, нет проблем с blackhole-роутингом у провайдеров
- **Поддержка WARP+** — опционально, ввод лицензионного ключа при установке
- **CLI-утилита** `vps-warp` — статус, трафик, ротация, обновление, удаление

## Установка

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/tagashi666/vps-warp/main/warp_install.sh)
```

Запускать от root. Скрипт спросит язык и опционально ключ WARP+.

Повторный запуск установщика, как и `vps-warp update`, сохраняет локальный порт, endpoint и выбор флага ниже, так что выход WARP после обновления остаётся прежним.

Флаг `--no-egress-check` выключает сверку страны выхода (см. [Страна выхода](#страна-выхода)), `--egress-check` включает обратно:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/tagashi666/vps-warp/main/warp_install.sh) --no-egress-check
```

Поддерживаются apt / dnf / yum / zypper / pacman / apk / emerge. Нужен systemd — на OpenRC-системах туннель придётся поднимать вручную, watchdog работать не будет.

## Управление

| Команда | Описание |
|---|---|
| `vps-warp` | Статус: IP туннеля, endpoint, страна выхода, handshake, состояние маршрутизации, трафик |
| `vps-warp start` | Запустить интерфейс |
| `vps-warp stop` | Остановить интерфейс |
| `vps-warp restart` | Перезапустить (endpoint и порт **сохраняются**) |
| `vps-warp rotate` | Сменить endpoint на случайный — новый жребий выхода. Локальный порт не меняется. На поднятом туннеле — без перезапуска |
| `vps-warp log` | Логи watchdog (история ротаций) |
| `vps-warp update` | Обновить до последней версии из репозитория (порт, endpoint и флаг **сохраняются**) |
| `vps-warp uninstall` | Полное удаление с подтверждением |

Строка `Routing:` в статусе показывает, на месте ли правило `fwmark 255 → table 51820`. Если там `MISSING` — трафик Xray уходит мимо туннеля, с реального IP сервера. Лечится через `vps-warp restart`.

Строка `Egress:` показывает страну выхода WARP и страну сервера так, как их видит Cloudflare. Если они не совпадают, watchdog сменит endpoint сам, а `vps-warp rotate` делает то же вручную. При выключенной проверке строка заканчивается на `check off`.

Строка `rp_filter:` показывает эффективное значение — ядро берёт `max(conf.all, conf.warp)`, поэтому смотреть на один только интерфейс бесполезно. `STRICT (=1)` означает, что обратный трафик дропается.

## Интеграция с Xray

После установки скрипт выведет локальный IP туннеля (вида `172.16.0.x`) и номер метки. Есть три способа направить трафик через WARP.

### Способ 1 — `sockopt.mark` (рекомендуется)

Работает вместе с политикой маршрутизации, которую ставит скрипт: пакеты с меткой 255 уходят в таблицу 51820.

```json
{
  "tag": "warp-out",
  "protocol": "freedom",
  "settings": {
    "domainStrategy": "ForceIPv4"
  },
  "streamSettings": {
    "sockopt": {
      "mark": 255
    }
  }
}
```

### Способ 2 — `sockopt.interface`

```json
{
  "tag": "warp-out",
  "protocol": "freedom",
  "settings": {
    "domainStrategy": "ForceIPv4"
  },
  "streamSettings": {
    "sockopt": {
      "interface": "warp",
      "tcpFastOpen": true
    }
  }
}
```

### Способ 3 — `sendThrough`

Если `sockopt` не поддерживается вашей версией Xray:

```json
{
  "tag": "warp-out",
  "protocol": "freedom",
  "sendThrough": "<LOCAL_WARP_IP>",
  "settings": {
    "domainStrategy": "ForceIPv4"
  }
}
```

`<LOCAL_WARP_IP>` — IP, который вывел скрипт после установки.

### Правило маршрутизации

```json
{
  "type": "field",
  "domain": [
    "geosite:openai",
    "domain:instagram.com",
    "domain:google.com"
  ],
  "outboundTag": "warp-out"
}
```

### Смена метки

Если 255 конфликтует с чем-то на сервере — поменяйте `WARP_FWMARK` в шапке `warp_install.sh` перед установкой. Значение попадёт в конфиг WireGuard, в watchdog и в вывод статуса автоматически.

## Как это работает

```
Xray/Sing-box
     │
     │  (трафик для заблокированных доменов, помечен fwmark 255)
     ▼
ip rule fwmark 255 → table 51820
     │
     ▼
warp (wg-quick интерфейс, MTU 1280)
     │
     │  WireGuard UDP
     ▼
188.114.9{6,7}.x:{2408,500,4500,1701}  ←── watchdog меняет endpoint при блокировке
     │
     ▼
Cloudflare WARP → целевой ресурс
```

Watchdog (`warp-watchdog.timer`) срабатывает каждые 3 минуты:

1. Проверяет, активен ли `wg-quick@warp`. Если вы остановили туннель сами — молча выходит
2. Смотрит возраст последнего handshake (порог — 180 секунд)
3. Пингует три DNS-резолвера с меткой 255, то есть ровно тем маршрутом, которым ходит Xray
4. Если туннель здоров — сверяет страну выхода со страной сервера (см. [Страна выхода](#страна-выхода)). Не совпала — до 5 раз меняет endpoint на живом интерфейсе, без перезапуска. С `--no-egress-check` шаг пропускается
5. Если туннель лежит — меняет `Endpoint` в `/etc/wireguard/warp.conf` и делает `systemctl restart wg-quick@warp`. `ListenPort` не трогает
6. Считает подряд идущие неудачи, включая несовпавшую страну. Пауза перед следующей попыткой растёт `3 → 6 → 12 → 24 → 30` минут и сбрасывается, как только всё в порядке

Смысл шестого шага: если Cloudflare недоступен целиком, ротация всё равно не поможет, а перезапуск WireGuard 480 раз в сутки — сам по себе заметный на потоке признак.

## Страна выхода

Cloudflare отдаёт каждую сессию WARP одной из машин ближайшего дата-центра и выбирает её по хешу внешней пары «наш адрес:порт → endpoint:порт». Часть машин выходит в интернет с адресов, которые сам Cloudflare относит к другой стране. С сервера в Токио примерно половина пар выходила с адресов `104.28.210.x` / `104.28.242.x`, помеченных как DE, остальные — с японских `104.28.211.x` / `104.28.243.x`. Одна и та же пара раз за разом даёт один и тот же выход, другая пара — новый жребий. Аккаунт WARP роли не играет: один и тот же аккаунт давал то JP, то DE.

### Закреплённый `ListenPort`

На этом держится всё остальное в разделе. Раз машину выхода выбирает пара, то пара и есть то, что определяет адрес и страну, с которыми туннель выходит в интернет. Endpoint скрипт хранил в конфиге всегда, а локальный порт — нет: без `ListenPort` ядро берёт новый порт при каждом `wg-quick up`. Значит, каждый перезапуск, перезагрузка или ротация давали новую пару, а с ней другую машину выхода — другой адрес и, возможно, другую страну. И происходило это молча.

Поэтому порт выбирается один раз, при первой установке, и дальше не меняется. `vps-warp rotate` и watchdog меняют только endpoint, а переустановка и `vps-warp update` сохраняют и порт, и endpoint. С закреплённым портом ключом к выходу служит один endpoint: тот же endpoint — тот же выход, новый endpoint — новый жребий. Новый жребий не обязательно приносит новый адрес: адресов выхода у дата-центра немного, и прежний выпадает часто.

Менять порт вдобавок к endpoint смысла нет. Оба одинаково перебрасывают жребий по одному и тому же набору машин дата-центра, а одних endpoint в пуле 2 × 254 × 4 = 2032 — на порядки больше, чем адресов выхода. Новых выходов смена порта не открывает, она лишь перемешивает всё соответствие «endpoint → выход» (замер — в разделе [Замеры и проверка](#замеры-и-проверка)).

Полной гарантии нет: Cloudflare может перераспределить машины и сам, поэтому watchdog страну и сверяет. Отсюда:

- сверка страны имеет смысл только с закреплённым портом: без него найденная пара терялась бы при первом же перезапуске
- с `--no-egress-check` порт закрепляется точно так же, и выход, выбранный вручную через `vps-warp rotate`, переживает перезапуски и обновления
- `vps-warp restart` и `vps-warp update` сохраняют пару; новый выход даёт только `vps-warp rotate`

Сменить сам порт можно руками: поправить `ListenPort` в `/etc/wireguard/warp.conf` и сделать `vps-warp restart` — либо удалить строку и переустановить, тогда установщик выберет новый. Все прежние соответствия «endpoint → выход» при этом перемешаются.

### Сверка страны

- страна сервера и страна выхода берутся из `https://1.1.1.1/cdn-cgi/trace` (поле `loc`): первая — запросом в обход туннеля, вторая — через `warp`. Если хоть одна не прочиталась, проверка пропускается, а туннель не трогается
- при несовпадении endpoint меняется на живом интерфейсе: пир удаляется и добавляется заново, сессия сбрасывается, и следующий пакет делает хэндшейк уже на новой паре — трафик возвращается примерно за 0,2 с. Установщик делает до 10 попыток, watchdog — до 5 за прогон

Почему не `systemctl restart`. Во-первых, `PostDown` у `wg-quick` снимает правило `fwmark 255`, и пока туннель лежит, помеченный трафик уходит с реального IP сервера. Во-вторых, несколько перезапусков подряд упираются в лимит systemd (5 запусков за 10 секунд), и юнит остаётся в `failed` — туннеля нет, пока кто-то не вмешается. Менять пару без сброса сессии тоже нельзя (замерено на смене порта): новая машина Cloudflare этой сессии не знает, и трафик стоит 5+ секунд, пока WireGuard не сделает хэндшейк сам.

### Как выключить

Совпадение страны выхода со страной сервера нужно не всегда, поэтому по умолчанию проверка включена, но её можно выключить.

- **Совпадение необходимо.** Сайт смотрит на страну адреса, и выход должен быть там же, где сервер, — как в случае с Токио выше: японский сервер, выходящий через «немецкую» машину, для таких сайтов превращается в немецкий. Для этого проверка и включена по умолчанию.
- **WARP ставят как раз ради другой страны.** Так делают особенно на российских узлах, чаще всего цепочкой WARP в WARP. На сервере это встречается редко, ведь проще сразу взять зарубежный, а на локальных машинах — часто. Здесь проверка работает против цели. Она перебрасывает endpoint, пока выход не окажется в стране сервера, то есть отнимает ровно ту страну, ради которой WARP и ставили. Если подходящей машины у Cloudflare нет, watchdog всё равно перебрасывает endpoint при каждом прогоне, с нарастающей паузой.
- **Несовпадение ничего не значит.** Например, нужным сайтам всё равно, из какой соседней страны пришёл запрос. Тогда проверка — это лишние запросы к `1.1.1.1` каждые 3 минуты и переброс endpoint, который каждый раз сбрасывает сессию.

Для последних двух случаев есть флаг `--no-egress-check`. Установщик и watchdog перестанут сверять страну и запрашивать `cdn-cgi/trace`, строка `Egress:` в статусе станет справочной. `ListenPort` по-прежнему закрепляется, поэтому выход, выбранный вручную через `vps-warp rotate`, переживает перезапуски и обновления.

Выбор хранится в маркере `/etc/vps-warp/no-egress-check` и переживает `vps-warp update`. Включить проверку обратно — переустановка с `--egress-check`. Можно и без переустановки: watchdog и `vps-warp` смотрят на маркер при каждом запуске, так что достаточно создать или удалить файл:

```bash
touch /etc/vps-warp/no-egress-check   # выключить
rm /etc/vps-warp/no-egress-check      # включить
```

Проверить страну выхода вручную:

```bash
curl -s --interface warp https://1.1.1.1/cdn-cgi/trace | grep loc   # выход WARP
curl -s https://1.1.1.1/cdn-cgi/trace | grep loc                    # сам сервер
```

## Замеры и проверка

### Как Cloudflare выбирает выход

**Токио**, два сервера, отдельный тестовый интерфейс (`Table = off`), рабочий туннель не трогался. Примерно половина пар выходила через машины, которые Cloudflare помечает как DE, остальные — как JP. Одна и та же пара давала один и тот же выход 3 раза из 3, смена порта перебрасывала жребий. Аккаунт WARP роли не играл: один и тот же аккаунт давал то JP, то DE.

**Нидерланды** (дата-центр Cloudflare AMS), тестовый сервер без пользователей, живой интерфейс `warp`, watchdog на время замера остановлен. Адрес выхода смотрели глазами двух внешних сайтов — `ifconfig.me` и `checkip.amazonaws.com`:

| Что менялось | Проб | Адресов выхода | Результат |
|---|---|---|---|
| ничего — одна и та же пара | 8 | 1 | шума нет: на одной паре всегда один адрес |
| только локальный порт, endpoint тот же | 20 | 5 | `104.28.251.137` ×10, `104.28.219.137` ×3, `104.28.251.140` ×3, `104.28.219.138` ×2, `104.28.219.139` ×2 |
| только endpoint, порт тот же | 20 | 4 | `104.28.251.137` ×8, `104.28.219.137` ×7, `104.28.251.140` ×4, `104.28.219.138` ×1 |
| возврат к уже пробованному endpoint | 5 | — | 5 из 5 — тот же адрес |
| возврат к уже пробованному порту | 5 | — | 4 из 5 — тот же адрес, один раз соседний (`.219.137` → `.219.138`) |

Выводы:

- порт и endpoint одинаково перебрасывают жребий по одному и тому же набору машин дата-центра; порт новых выходов не открывает
- с закреплённым портом endpoint — ключ к выходу: старый endpoint возвращает старый выход, новый — новый жребий, а не обязательно новый адрес
- поле `ip` у `https://1.1.1.1/cdn-cgi/trace` в AMS не совпадало с адресом, который видят внешние сайты: для страны поле `loc` годится, а адрес выхода надо смотреть внешним сайтом

Повторить замер можно только на машине без пользователей — пара меняется на живом интерфейсе:

```bash
systemctl stop warp-watchdog.timer
PUB=$(wg show warp peers); P=$(wg show warp listen-port)
try() {   # try <порт> <endpoint>
    wg set warp listen-port "$1" peer "$PUB" remove
    wg set warp peer "$PUB" endpoint "$2" allowed-ips 0.0.0.0/0 persistent-keepalive 15
    echo "$1 $2 $(curl -4 -s -m 6 --interface warp https://ifconfig.me/ip)"
}
try "$P" 188.114.96.10:2408; try "$P" 188.114.97.20:500; try "$P" 188.114.96.10:2408
systemctl restart wg-quick@warp && systemctl start warp-watchdog.timer   # вернуть пару из конфига
```

### Проверка установщика

Сервер в Нидерландах (Debian 13), установка под pty в форме `bash <(…)`, то есть тем же путём, что и `bash <(curl …)`. Переброс по стране вызывался принудительно — страной сервера, подменённой на `XX`.

| Сценарий | Результат |
|---|---|
| неизвестный аргумент | ошибка до любых изменений, туннель не тронут, маркер не создан |
| `--no-egress-check` | шаг сверки пропущен, маркер создан, watchdog не делает ни одного запроса, в статусе `check off` |
| повторная установка без аргументов (так её запускает `vps-warp update`) | сверка остаётся выключенной |
| `--egress-check` | маркер удалён, сверка снова идёт при установке и в watchdog |
| `touch` / `rm` маркера без переустановки | 0 и 2 запроса за прогон watchdog |
| установка с GitHub: `bash <(curl …) --no-egress-check` | флаг доходит, результат тот же |
| переустановка поверх v4.0 | «Port and endpoint kept», порт, endpoint и адрес выхода те же |
| `vps-warp rotate` | endpoint новый, порт тот же, пауза watchdog сброшена |
| watchdog, несовпадение страны | 5 перебросов endpoint на живом интерфейсе, порт тот же, затем пауза |
| watchdog, туннель лёг | новый endpoint и `systemctl restart`, после перезапуска порт тот же |
| установщик, несовпадение страны | 10 перебросов endpoint, порт тот же, предупреждение |
| конфиг без `ListenPort`, как после v3.4 | новый порт, endpoint сохранён |
| установка без конфига | порт и endpoint новые |
| `vps-warp update`, когда в репозитории версия старше | «Installed v4.0 is newer», ничего не меняется |

## Почему нужен нестрогий rp_filter

Туннель асимметричен by design: помеченные пакеты Xray уходят через `warp` (таблица 51820), а дефолтный маршрут сервера остаётся на основном интерфейсе. Расшифрованные ответы возвращаются на `warp` **без метки** — правило `fwmark 255` не срабатывает, лукап уходит в main table, упирается в дефолт через основной NIC, входящий интерфейс не совпадает. Строгий rp_filter такой пакет отбрасывает.

Симптом коварный: `wg show` показывает свежий handshake, `vps-warp` пишет `ACTIVE`, а трафика через туннель нет.

`wg-quick` эту ситуацию не закрывает. Его `sysctl net.ipv4.conf.all.src_valid_mark=1` живёт внутри `add_default()`, а `add_route()` попадает туда только при `Table = auto` или пустом `Table`. С явным `Table = 51820` берётся другая ветка, и `src_valid_mark` не выставляется никогда.

### Почему это не решается силами Xray

Xray умеет отключать `rp_filter` сам, но делает это только в `proxy/wireguard/tun_linux.go` — на kernel-TUN пути **встроенного** WireGuard-протокола. То есть срабатывает лишь при outbound/inbound с `"protocol": "wireguard"`, и внутри контейнера с read-only `/proc/sys` падает (`failed to disable ipv4 rp_filter for all: read-only file system`).

При нашей схеме Xray этот код не выполняет вообще: туннель ядерный, Xray ходит в него обычным `freedom` + `sockopt.mark`. Отсюда два следствия:

- **`privileged: true` для этой схемы не нужен.** Достаточно `NET_ADMIN` в docker-compose ноды — `SO_MARK` требует `CAP_NET_ADMIN`, не более
- **rp_filter обязан настроить кто-то на хосте**, потому что Xray про ядерный туннель ничего не знает. Этим и занимается скрипт

Если на ноде всё же используется встроенный WG-outbound Xray и он не стартует из-за rp_filter — помимо `privileged: true` есть вариант мягче: `"noKernelTun": true` в settings, откат на userspace-стек gVisor, которому привилегии не нужны. Ценой производительности.

Выбран loose (`=2`), а не `0`: он по-прежнему отбрасывает мартиан и немаршрутизируемые источники, разрешая только асимметричный путь. Скрипт трогает **только** значение `1` — если вы осознанно поставили `0`, оно останется.

## Файлы

| Путь | Что это |
|---|---|
| `/etc/wireguard/warp.conf` | Конфиг туннеля (0600, содержит приватный ключ и закреплённый `ListenPort`) |
| `/etc/vps-warp/wgcf/` | Рабочая директория wgcf: `wgcf-account.toml` |
| `/etc/vps-warp/version` | Установленная версия, для `vps-warp update` |
| `/etc/vps-warp/watchdog.state` | Счётчик неудач (включая несовпавшую страну выхода) и время последней ротации |
| `/etc/vps-warp/no-egress-check` | Маркер: сверка страны выхода выключена (создаётся флагом `--no-egress-check`) |
| `/opt/vps-warp/watchdog.sh` | Скрипт watchdog |
| `/usr/local/bin/vps-warp` | CLI |
| `/usr/local/bin/wgcf` | Бинарь wgcf |
| `/etc/sysctl.d/99-vps-warp.conf` | Закреплённый rp_filter (создаётся только если он был строгим) |

## Удаление

```bash
vps-warp uninstall
```

Снимет сервисы, удалит `ip rule` и правило MSS, погасит интерфейс, уберёт sysctl-файл и почистит все данные. Пакет `wireguard` остаётся установленным — при желании снесите руками.
