# VPS-WARP

**Cloudflare WARP на вашем VPS без официального клиента.**  
Нативный WireGuard + умный watchdog с авто-ротацией endpoint. Сделан для работы с Xray-core, Remnawave, 3X-UI и Marzban.

Форк [tagashi666/vps-warp](https://github.com/tagashi666/vps-warp); с версии 5.0 развивается здесь.

---

## Зачем

Хостинги блокируют, Cloudflare шейпит трафик из датацентров — WARP перестаёт работать. Стандартный `warp-cli` жирный и капризный.

VPS-WARP поднимает туннель через `wg-quick` и ставит systemd-watchdog, который каждые 3 минуты пингует `1.1.1.1`, `8.8.8.8` и `9.9.9.9` через туннель. Если пинг не проходит или хэндшейк не обновлялся больше 3 минут — скрипт меняет endpoint на случайный из пула Cloudflare и перезапускает туннель. Тихо, без вашего участия.

---

## Особенности

- **Нативный WireGuard** — никаких проприетарных демонов Cloudflare
- **Авто-ротация endpoint** — при падении связи выбирает случайный адрес из `188.114.{96,97}.x` на портах `2408 / 500 / 4500 / 1701`. Локальный порт при этом не меняется
- **Закреплённый `ListenPort`** — Cloudflare выбирает машину выхода по паре «наш адрес:порт → endpoint:порт», то есть пара определяет адрес и страну выхода. Порт выбирается один раз, при первой установке, и дальше не меняется — ни ротацией, ни переустановкой, ни `vps-warp update`. Поэтому ключ к выходу — endpoint: тот же endpoint, как правило, — тот же выход, новый — новый жребий (см. [Закреплённый ListenPort](#закреплённый-listenport))
- **Страна выхода как у сервера** — часть машин Cloudflare выходит с адресов, которые он сам относит к другой стране. Скрипт сверяет страну выхода при установке и на каждом прогоне watchdog и при несовпадении меняет endpoint на живом интерфейсе. Выключается флагом `--no-egress-check` (см. [Страна выхода](#страна-выхода))
- **Изолированная маршрутизация** — отдельная таблица 51820 + правило `ip rule fwmark 255`. Основной трафик сервера не затрагивается: в туннель уходит только то, что помечено меткой 255 (см. [Интеграция с Xray](#интеграция-с-xray))
- **Несколько аккаунтов** — флаг `--accounts N`: соединения раскладываются по N аккаунтам WARP. Cloudflare ограничивает число новых соединений на одно устройство, и нагруженному серверу одного аккаунта не хватает (см. [Несколько аккаунтов](#несколько-аккаунтов))
- **TCP MSS Clamping** — правило в `mangle POSTROUTING` на исходящих через `warp`, MSS 1240 при MTU 1280. Предотвращает зависания на тяжёлых сайтах
- **Backoff при ротации** — если Cloudflare заблокирован целиком, watchdog не дёргает туннель каждые 3 минуты, а наращивает паузу до 30 минут
- **rp_filter** — при строгом режиме (`=1`, дефолт RHEL/Rocky/Alma) обратный трафик туннеля дропается ядром. Скрипт понижает до loose (`=2`) и закрепляет в `/etc/sysctl.d/99-vps-warp.conf`. На Ubuntu, где уже `=2`, ничего не трогает
- **IPv4 и IPv6** — с версии 5.1 IPv6 через WARP включён: открываются сайты только с IPv6, а Google оценивает протоколы по отдельности. Выключается флагом `--no-ipv6` (см. [IPv6](#ipv6))
- **Поддержка WARP+** — опционально, ввод лицензионного ключа при установке
- **CLI-утилита** `vps-warp` — статус, трафик, ротация, обновление, удаление

## Установка

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Chara-Freedom/vps-warp/main/warp_install.sh)
```

Запускать от root. Скрипт спросит язык и опционально ключ WARP+.

Повторный запуск установщика, как и `vps-warp update`, сохраняет локальный порт, endpoint и выбор флагов ниже, так что выход WARP после обновления остаётся прежним. Работающий туннель установщик трогает, только когда новый конфиг уже готов: если загрузка wgcf, регистрация или генерация профиля не удались, WARP продолжает работать как раньше.

Флаг `--no-egress-check` выключает сверку страны выхода (см. [Страна выхода](#страна-выхода)), `--egress-check` включает обратно:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Chara-Freedom/vps-warp/main/warp_install.sh) --no-egress-check
```

Флаг `--no-ipv6` оставляет WARP только на IPv4, как до версии 5.1, `--ipv6` включает обратно (см. [IPv6](#ipv6)).

Флаг `--accounts N` (от 1 до 10) задаёт число аккаунтов WARP, по которым раскладываются соединения (см. [Несколько аккаунтов](#несколько-аккаунтов)). Без флага остаётся прежнее число, при первой установке — один:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Chara-Freedom/vps-warp/main/warp_install.sh) --accounts 3
```

Если vps-warp ставился из исходного репозитория `tagashi666/vps-warp`, `vps-warp update` смотрит туда. Перейти сюда можно один раз переустановкой командой выше: порт, endpoint и аккаунт сохранятся.

Поддерживаются apt / dnf / yum / zypper / pacman / apk / emerge. Нужен systemd — на OpenRC-системах туннель придётся поднимать вручную, watchdog работать не будет.

## Управление

| Команда | Описание |
|---|---|
| `vps-warp` | Статус: IP туннеля, endpoint, страна выхода, handshake, состояние маршрутизации, трафик |
| `vps-warp start` | Запустить интерфейс |
| `vps-warp stop` | Остановить интерфейс |
| `vps-warp restart` | Перезапустить (endpoint и порт **сохраняются**) |
| `vps-warp rotate` | Сменить endpoint на случайный — новый жребий выхода. Локальный порт не меняется. На поднятом туннеле — без перезапуска |
| `vps-warp log` | Логи watchdog (история ротаций) |
| `vps-warp update` | Обновить до последней версии из репозитория (порт, endpoint, флаги и аккаунты **сохраняются**) |
| `vps-warp uninstall` | Полное удаление с подтверждением |

С несколькими аккаунтами `start`, `stop`, `restart` и `rotate` действуют на все интерфейсы, а с именем интерфейса — на один: `vps-warp rotate warp2`. Статус показывает каждый аккаунт отдельно.

Строка `Routing:` в статусе показывает, на месте ли правило `fwmark 255 → table 51820` и маршрут в этой таблице; с несколькими аккаунтами — ещё и интерфейсы, по которым маршрут сейчас раскладывает соединения. Если там `MISSING` или `NO ROUTE` — трафик Xray уходит мимо туннеля, с реального IP сервера. Watchdog восстанавливает их сам при следующем прогоне, вручную — `vps-warp restart`.

Строка `Egress:` показывает страну выхода WARP и страну сервера так, как их видит Cloudflare. Если они не совпадают, watchdog сменит endpoint сам, а `vps-warp rotate` делает то же вручную. При выключенной проверке строка заканчивается на `check off`.

Строка `rp_filter:` показывает эффективное значение — ядро берёт `max(conf.all, conf.warp)`, поэтому смотреть на один только интерфейс бесполезно. `STRICT (=1)` означает, что обратный трафик дропается.

## Интеграция с Xray

После установки скрипт выведет локальный IP туннеля (вида `172.16.0.x`) и номер метки. Есть три способа направить трафик через WARP.

### Способ 1 — `sockopt.mark` (рекомендуется)

Работает вместе с политикой маршрутизации, которую ставит скрипт: пакеты с меткой 255 уходят в таблицу 51820. Только этот способ раскладывает соединения по нескольким аккаунтам: способы 2 и 3 привязаны к одному интерфейсу, то есть к первому аккаунту. Конфиг Xray при переходе на несколько аккаунтов не меняется.

`ForceIPv4v6` — сначала IPv4, а если у домена нет A-записи, то IPv6 через WARP (см. [IPv6](#ipv6)). `Force` значит: если Xray не разрешил домен сам, соединение не устанавливается, а не уходит в систему «как есть»; вариант `UseIPv4v6` панель Remnawave помечает предупреждением. С `--no-ipv6` здесь нужен `ForceIPv4`: иначе соединение на IPv6-адрес уйдёт мимо туннеля, с собственного IPv6 сервера.

```json
{
  "tag": "warp-out",
  "protocol": "freedom",
  "settings": {
    "domainStrategy": "ForceIPv4v6"
  },
  "streamSettings": {
    "sockopt": {
      "mark": 255
    }
  }
}
```

### Способ 2 — `sockopt.interface`

Способы 2 и 3 — только IPv4: IPv6 через WARP проверен со способом 1.

```json
{
  "tag": "warp-out",
  "protocol": "freedom",
  "settings": {
    "domainStrategy": "ForceIPv4"
  },
  "streamSettings": {
    "sockopt": {
      "interface": "warp",
      "tcpFastOpen": true
    }
  }
}
```

### Способ 3 — `sendThrough`

Если `sockopt` не поддерживается вашей версией Xray:

```json
{
  "tag": "warp-out",
  "protocol": "freedom",
  "sendThrough": "<LOCAL_WARP_IP>",
  "settings": {
    "domainStrategy": "ForceIPv4"
  }
}
```

`<LOCAL_WARP_IP>` — IP, который вывел скрипт после установки.

### Правило маршрутизации

```json
{
  "type": "field",
  "domain": [
    "geosite:openai",
    "domain:instagram.com",
    "domain:google.com"
  ],
  "outboundTag": "warp-out"
}
```

### Смена метки

Если 255 конфликтует с чем-то на сервере — поменяйте `WARP_FWMARK` в шапке `warp_install.sh` перед установкой. Значение попадёт в конфиг WireGuard, в watchdog и в вывод статуса автоматически.

## Как это работает

```
Xray/Sing-box
     │
     │  (трафик для заблокированных доменов, помечен fwmark 255)
     ▼
ip rule fwmark 255 → table 51820
     │
     │  с --accounts N: многопутевой маршрут, соединение — на один интерфейс по хешу
     ▼
warp, warp2, … (wg-quick интерфейсы, MTU 1280, по одному на аккаунт)
     │
     │  WireGuard UDP
     ▼
188.114.9{6,7}.x:{2408,500,4500,1701}  ←── watchdog меняет endpoint при блокировке
     │
     ▼
Cloudflare WARP → целевой ресурс
```

Маршрут таблицы 51820 и правило `fwmark` строит `/opt/vps-warp/routes.sh`, его вызывает каждый интерфейс при подъёме (`PostUp`) и перед остановкой (`PreDown`). Интерфейсы поднимаются с `Table = off`, так что `wg-quick` своих маршрутов и правил не ставит. Правило снимается, когда гаснет последний интерфейс. Для IPv6 то же самое — правило `ip -6 rule fwmark 255` и маршрут в той же таблице, только через один аккаунт (см. [IPv6](#ipv6)).

Watchdog (`warp-watchdog.timer`) срабатывает каждые 3 минуты и проверяет каждый аккаунт отдельно:

1. Проверяет, активен ли `wg-quick@<интерфейс>`. Если вы остановили его сами — молча пропускает
2. Смотрит возраст последнего handshake (порог — 180 секунд)
3. Пингует три DNS-резолвера через сам интерфейс (`ping -I`). Не по метке 255: с несколькими аккаунтами помеченный пинг ушёл бы в тот интерфейс, который выберет хеш
4. Если туннель здоров — сверяет страну выхода со страной сервера (см. [Страна выхода](#страна-выхода)). Не совпала — до 5 раз меняет endpoint на живом интерфейсе, без перезапуска. С `--no-egress-check` шаг пропускается
5. Если туннель лежит — с несколькими аккаунтами сначала выводит его из маршрута, затем меняет `Endpoint` в его конфиге и делает `systemctl restart wg-quick@<интерфейс>`. `ListenPort` не трогает. В маршрут интерфейс вернётся, когда очередной прогон найдёт его здоровым
6. Считает подряд идущие неудачи, включая несовпавшую страну. Пауза перед следующей попыткой растёт `3 → 6 → 12 → 24 → 30` минут и сбрасывается, как только всё в порядке
7. Если правило `fwmark` или маршрут пропали при поднятом туннеле — строит их заново

Смысл шестого шага: если Cloudflare недоступен целиком, ротация всё равно не поможет, а перезапуск WireGuard 480 раз в сутки — сам по себе заметный на потоке признак.

## Несколько аккаунтов

Cloudflare ограничивает, сколько новых соединений принимает одно устройство WARP. Пока сервер открывает их немного, ограничения не видно. На нагруженном сервере часть SYN остаётся без ответа: соединения через WARP устанавливаются за секунды или не устанавливаются вовсе, а снаружи это выглядит как долгие TLS-рукопожатия и таймауты сайтов. Смена endpoint помогает на пару минут, WARP+ не помогает вовсе, а второй, бесплатный аккаунт на том же сервере, с тем же endpoint и тем же адресом выхода, отвечает сразу (замер — в разделе [Лимит на устройство](#лимит-на-устройство)).

`--accounts N` поднимает по интерфейсу на аккаунт: `warp`, `warp2`, … Маршрут таблицы 51820 становится многопутевым, и ядро раскладывает соединения по хешу адресов и портов (`net.ipv4.fib_multipath_hash_policy = 1`, закрепляется в `/etc/sysctl.d/99-vps-warp-multipath.conf`). Каждое соединение всё время идёт через один аккаунт. Внутренний адрес у всех устройств WARP одинаковый, `172.16.0.2`, поэтому конфиг Xray не меняется.

У каждого аккаунта свой закреплённый порт, свой endpoint и своя сверка страны выхода. Переустановка и `vps-warp update` сохраняют все аккаунты, а переустановка с меньшим `N` удаляет лишние вместе с их файлами.

Что нужно знать:

- **Мёртвый аккаунт выводится из маршрута.** Пока он в маршруте, его доля соединений пропадает. Watchdog замечает это за один прогон (до 3 минут) и выводит интерфейс из маршрута. Последний живой интерфейс не выводится никогда, поэтому с одним аккаунтом всё как раньше
- **Возвращение в маршрут рвёт часть соединений.** Когда интерфейс возвращается, раскладка хеша меняется, и часть уже открытых соединений других аккаунтов уходит в него. Этот аккаунт таких соединений не знает, и они обрываются, как при любом перезапуске. Бывает это только после того, как аккаунт падал
- **Маршрут собирается в `PreDown`, а не в `PostDown`.** Если удалить интерфейс, на который указывает многопутевой маршрут, ядро удаляет маршрут целиком, вместе с долей остальных аккаунтов. Поэтому перед остановкой интерфейса маршрут пересобирается без него
- **WARP+ лимит не поднимает** — проверено (см. [Лимит на устройство](#лимит-на-устройство)), поэтому для пула хватает бесплатных аккаунтов. Ключ, введённый при установке, применяется только к первому аккаунту
- **Регистрация.** Новые аккаунты регистрируются с паузой в несколько секунд: Cloudflare ограничивает частоту регистраций

Понять, что аккаунтов не хватает, можно по числу соединений через WARP, которые ждут ответа на SYN. Единицы — норма, сотни и тысячи — признак лимита:

```bash
ss -tanH state syn-sent src 172.16.0.2 | wc -l
```

## IPv6

До версии 5.1 IPv6 из профиля WARP вырезался — в исходном репозитории со ссылкой на «blackhole-роутинг у провайдеров», без подробностей. Туннель был только IPv4, и сайты без A-записи через WARP не открывались вовсе: их приходилось пускать мимо WARP. С 5.1 IPv6-адрес и маршрут `::/0` из профиля остаются, скрипт ставит правило `ip -6 rule fwmark 255`, маршрут в таблице 51820 и ограничение MSS 1220 через `ip6tables`.

Замер перед включением — три сервера, тестовый интерфейс в отдельном сетевом пространстве, рабочие туннели не трогались:

| | Сервер 1 (AMS) | Сервер 2 (NRT) | Сервер 3 (AMS) |
|---|---|---|---|
| сайт только с IPv6 (ntc.party) | 10 из 10 | 10 из 10 | 10 из 10 |
| ping, IPv4 / IPv6 | 2,0 / 2,2 мс, без потерь | 1,4 / 1,5 мс, без потерь | 29 / 29 мс, без потерь |
| скачивание, IPv4 / IPv6 | 429 от сервера / 26 МБ/с | 53–58 / 53–55 МБ/с | 21–22 / 21–24 МБ/с |
| `GL` YouTube, IPv4 / IPv6 | RU / RU | JP / JP | RU / US |

Google, YouTube, Wikipedia и сайт Cloudflare по IPv6 открывались так же, как по IPv4. Зависаний, ради которых IPv6 вырезали, не было ни разу. На третьем сервере видно, что Google оценивает протоколы по отдельности: по IPv4 YouTube счёл выход российским, по IPv6 — американским. Gemini по IPv6 в AMS отказывал (ошибка 1060), так что гарантии нет, но шанс, что IPv6 пройдёт там, где IPv4 отказывают, есть.

Что нужно знать:

- **Xray.** Чтобы пользоваться IPv6, у `warp-out` нужен `"domainStrategy": "ForceIPv4v6"` (см. [Способ 1](#способ-1--sockoptmark-рекомендуется)): домены с A-записью по-прежнему идут по IPv4, по IPv6 — только сайты без неё. С `ForceIPv4` всё работает как до 5.1, IPv6 в туннеле просто не используется. Чтобы отдельные сайты шли именно по IPv6, нужен второй аутбаунд с той же меткой и `"domainStrategy": "ForceIPv6"` и правило маршрутизации на него
- **Несколько аккаунтов.** IPv6 идёт через один аккаунт — первый живой — с явным исходным адресом в маршруте. По IPv4 у всех устройств WARP общий адрес `172.16.0.2`, а по IPv6 у каждого свой, и Cloudflare принимает пакеты только с него. При раскладке хешем соединение после любой пересборки маршрута могло бы уйти через чужой аккаунт со своим адресом и умереть. Если первый аккаунт выведен из маршрута, IPv6 переезжает на следующий
- **Собственный IPv6 сервера** не трогается: в туннель идёт только помеченный трафик, а исходный адрес задан в маршруте, поэтому помеченное соединение не выйдет с адреса сервера
- **Выключить** — переустановка с `--no-ipv6` (маркер `/etc/vps-warp/no-ipv6`, переживает `vps-warp update`), включить обратно — `--ipv6`. Если IPv6 выключен в ядре (`disable_ipv6`), установщик оставляет WARP только на IPv4 и предупреждает об этом
- **Утечка при `--no-ipv6`.** Без IPv6 в туннеле помеченное соединение на IPv6-адрес под правило не попадает и уходит с собственного IPv6 сервера. Поэтому с `--no-ipv6` у `warp-out` нужен `ForceIPv4`

Строка `IPv6:` в статусе показывает, на месте ли правило и маршрут и через какой интерфейс идёт IPv6.

## Страна выхода

Cloudflare отдаёт каждую сессию WARP одной из машин ближайшего дата-центра и выбирает её по хешу внешней пары «наш адрес:порт → endpoint:порт». Часть машин выходит в интернет с адресов, которые сам Cloudflare относит к другой стране. С сервера в Токио примерно половина пар выходила с адресов `104.28.210.x` / `104.28.242.x`, помеченных как DE, остальные — с японских `104.28.211.x` / `104.28.243.x`. Одна и та же пара раз за разом даёт один и тот же выход, другая пара — новый жребий. Аккаунт WARP роли не играет: один и тот же аккаунт давал то JP, то DE.

### Закреплённый `ListenPort`

На этом держится всё остальное в разделе. Раз машину выхода выбирает пара, то пара и есть то, что определяет адрес и страну, с которыми туннель выходит в интернет. Endpoint скрипт хранил в конфиге всегда, а локальный порт — нет: без `ListenPort` ядро берёт новый порт при каждом `wg-quick up`. Значит, каждый перезапуск, перезагрузка или ротация давали новую пару, а с ней другую машину выхода — другой адрес и, возможно, другую страну. И происходило это молча.

Поэтому порт выбирается один раз, при первой установке, и дальше не меняется. `vps-warp rotate` и watchdog меняют только endpoint, а переустановка и `vps-warp update` сохраняют и порт, и endpoint. С закреплённым портом ключом к выходу служит один endpoint: тот же endpoint, как правило, возвращает тот же выход, новый endpoint — новый жребий. Новый жребий не обязательно приносит новый адрес: адресов выхода у дата-центра немного, и прежний выпадает часто.

Менять порт вдобавок к endpoint смысла нет. Оба одинаково перебрасывают жребий по одному и тому же набору машин дата-центра, а одних endpoint в пуле 2 × 254 × 4 = 2032 — на порядки больше, чем адресов выхода. Новых выходов смена порта не открывает, она лишь перемешивает всё соответствие «endpoint → выход» (замер — в разделе [Замеры и проверка](#замеры-и-проверка)).

Полной гарантии нет. За три минуты замера из 30 закреплённых пар 22 ни разу не сменили выход, три один раз переехали на другой адрес, а две выходили попеременно с двух адресов — Cloudflare перераспределяет машины и сам. Перезапуск интерфейса тут ничего не добавляет, и смена порта от этого не спасает: без закрепления выход меняется уже при каждом перезапуске. Поэтому watchdog страну и сверяет. Отсюда:

- сверка страны имеет смысл только с закреплённым портом: без него найденная пара терялась бы при первом же перезапуске
- с `--no-egress-check` порт закрепляется точно так же, и выход, выбранный вручную через `vps-warp rotate`, переживает перезапуски и обновления
- `vps-warp restart` и `vps-warp update` сохраняют пару; новый выход даёт только `vps-warp rotate`

Сменить сам порт можно руками: поправить `ListenPort` в `/etc/wireguard/warp.conf` и сделать `vps-warp restart` — либо удалить строку и переустановить, тогда установщик выберет новый. Все прежние соответствия «endpoint → выход» при этом перемешаются.

### Сверка страны

- страна сервера и страна выхода берутся из `https://1.1.1.1/cdn-cgi/trace` (поле `loc`): первая — запросом в обход туннеля, вторая — через `warp`. Если хоть одна не прочиталась, проверка пропускается, а туннель не трогается
- при несовпадении endpoint меняется на живом интерфейсе: пир удаляется и добавляется заново, сессия сбрасывается, и следующий пакет делает хэндшейк уже на новой паре — трафик возвращается примерно за 0,2 с. Установщик делает до 10 попыток, watchdog — до 5 за прогон

Почему не `systemctl restart`. Во-первых, `PostDown` у `wg-quick` снимает правило `fwmark 255`, и пока туннель лежит, помеченный трафик уходит с реального IP сервера. Во-вторых, несколько перезапусков подряд упираются в лимит systemd (5 запусков за 10 секунд), и юнит остаётся в `failed` — туннеля нет, пока кто-то не вмешается. Менять пару без сброса сессии тоже нельзя (замерено на смене порта): новая машина Cloudflare этой сессии не знает, и трафик стоит 5+ секунд, пока WireGuard не сделает хэндшейк сам.

### Как выключить

Совпадение страны выхода со страной сервера нужно не всегда, поэтому по умолчанию проверка включена, но её можно выключить.

- **Совпадение необходимо.** Сайт смотрит на страну адреса, и выход должен быть там же, где сервер, — как в случае с Токио выше: японский сервер, выходящий через «немецкую» машину, для таких сайтов превращается в немецкий. Для этого проверка и включена по умолчанию.
- **WARP ставят как раз ради другой страны.** Так делают особенно на российских узлах, чаще всего цепочкой WARP в WARP. На сервере это встречается редко, ведь проще сразу взять зарубежный, а на локальных машинах — часто. Здесь проверка работает против цели. Она перебрасывает endpoint, пока выход не окажется в стране сервера, то есть отнимает ровно ту страну, ради которой WARP и ставили. Если подходящей машины у Cloudflare нет, watchdog всё равно перебрасывает endpoint при каждом прогоне, с нарастающей паузой.
- **Несовпадение ничего не значит.** Например, нужным сайтам всё равно, из какой соседней страны пришёл запрос. Тогда проверка — это лишние запросы к `1.1.1.1` каждые 3 минуты и переброс endpoint, который каждый раз сбрасывает сессию.

Для последних двух случаев есть флаг `--no-egress-check`. Установщик и watchdog перестанут сверять страну и запрашивать `cdn-cgi/trace`, строка `Egress:` в статусе станет справочной. `ListenPort` по-прежнему закрепляется, поэтому выход, выбранный вручную через `vps-warp rotate`, переживает перезапуски и обновления.

Выбор хранится в маркере `/etc/vps-warp/no-egress-check` и переживает `vps-warp update`. Включить проверку обратно — переустановка с `--egress-check`. Можно и без переустановки: watchdog и `vps-warp` смотрят на маркер при каждом запуске, так что достаточно создать или удалить файл:

```bash
touch /etc/vps-warp/no-egress-check   # выключить
rm /etc/vps-warp/no-egress-check      # включить
```

Проверить страну выхода вручную:

```bash
curl -s --interface warp https://1.1.1.1/cdn-cgi/trace | grep loc   # выход WARP
curl -s https://1.1.1.1/cdn-cgi/trace | grep loc                    # сам сервер
```

## Замеры и проверка

### Как Cloudflare выбирает выход

**Токио**, два сервера, отдельный тестовый интерфейс (`Table = off`), рабочий туннель не трогался. Примерно половина пар выходила через машины, которые Cloudflare помечает как DE, остальные — как JP. Одна и та же пара давала один и тот же выход 3 раза из 3, смена порта перебрасывала жребий. Аккаунт WARP роли не играл: один и тот же аккаунт давал то JP, то DE.

**Нидерланды** (дата-центр Cloudflare AMS), тестовый сервер без пользователей, живой интерфейс `warp`, watchdog на время замера остановлен. Адрес выхода смотрели внешние сайты (`checkip.amazonaws.com`, во втором замере ещё и `ifconfig.me`), пустых ответов не было ни одного.

**Отнимает ли закреплённый порт выходы.** 120 раундов, в каждом по одной пробе пяти серий подряд, чтобы дрейф во времени задевал все серии одинаково (600 проб за 2 минуты):

| Серия | `219.137` | `251.137` | `219.139` | `251.139` | `251.140` | `219.138` | `251.138` | `219.140` | адресов |
|---|---|---|---|---|---|---|---|---|---|
| порт и endpoint случайные (как до v4.0) | 22 | 29 | 16 | 14 | 8 | 11 | 10 | 10 | 8 |
| меняется только порт | 19 | 23 | 18 | 9 | 19 | 15 | 9 | 8 | 8 |
| закреплён порт №1, меняется endpoint | 28 | 24 | 10 | 14 | 8 | 14 | 15 | 7 | 8 |
| закреплён порт №2, меняется endpoint | 28 | 20 | 12 | 16 | 12 | 12 | 12 | 8 | 8 |
| закреплён порт №3, меняется endpoint | 29 | 22 | 12 | 13 | 15 | 8 | 14 | 7 | 8 |

Адреса — `104.28.x.y`. Каждая серия увидела все 8 адресов, встретившихся за 600 проб. Самый редкий, `219.140`, выпал в 40 пробах из 600; если бы закрепление порта его отнимало, серия из 120 проб пропустила бы его случайно с вероятностью около 0,00025. Распределения не различаются: однородность пяти серий по хи-квадрат p = 0,74, закреплённые порты против меняющегося p = 0,19. Утверждение касается адресов, которые вообще встретились: адрес с долей меньше ~2% мог не выпасть ни в одной серии. В первом, мелком замере (по 20 проб) серии видели 4–5 адресов из этих восьми — для такого вывода 20 проб мало.

**Одинаков ли выход у одной и той же пары.** 30 случайных пар «порт → endpoint», 350 проб за 3 минуты, каждую пробу смотрели оба сайта: 10 кругов живой смены пары (так её меняют `rotate` и watchdog), 2 круга на 10 из них через запись в конфиг и `systemctl restart wg-quick@warp`, затем ещё круг живой сменой:

| Поведение | Пар | Что видно |
|---|---|---|
| выход ни разу не менялся | 22 | 13 проб × 2 сайта, одинаково при живой смене и после перезапуска |
| одиночный сбой | 3 | в одной пробе один сайт увидел соседний адрес, в остальных 12 — прежний |
| один раз переехали, дальше стабильно | 3 | например, `219.139` → `219.138` на 9-м круге |
| попеременно два адреса | 2 | `219.139` / `251.140` и `219.137` / `251.137`, иногда два сайта в одной пробе видят разное |

Соседние пробы одной пары совпали в 293 случаях из 320 (91,6%), без двух мигающих пар — около 98%. После перезапуска интерфейса каждая пара давала то же, что живой сменой в это же время. Без закреплённого порта каждый перезапуск — новый жребий, и по долям адресов выше он сохраняет прежний выход лишь примерно в 14% случаев.

Выводы:

- порт и endpoint одинаково перебрасывают жребий по одному и тому же набору машин дата-центра; закреплённый порт выходов не отнимает
- с закреплённым портом endpoint — ключ к выходу: тот же endpoint, как правило, возвращает тот же выход, новый — новый жребий, а не обязательно новый адрес
- гарантии нет: Cloudflare сам иногда переносит пару на другой адрес, а у части пар держит два адреса сразу, выбирая их на каждое соединение. Смена порта от этого не спасает
- поле `ip` у `https://1.1.1.1/cdn-cgi/trace` в AMS не совпадало с адресом, который видят внешние сайты: для страны поле `loc` годится, а адрес выхода надо смотреть внешним сайтом

Повторить замер можно только на машине без пользователей — пара меняется на живом интерфейсе:

```bash
systemctl stop warp-watchdog.timer
PUB=$(wg show warp peers); P=$(wg show warp listen-port)
try() {   # try <порт> <endpoint>
    wg set warp listen-port "$1" peer "$PUB" remove
    wg set warp peer "$PUB" endpoint "$2" allowed-ips 0.0.0.0/0 persistent-keepalive 15
    echo "$1 $2 $(curl -4 -s -m 6 --interface warp https://ifconfig.me/ip)"
}
try "$P" 188.114.96.10:2408; try "$P" 188.114.97.20:500; try "$P" 188.114.96.10:2408
systemctl restart wg-quick@warp && systemctl start warp-watchdog.timer   # вернуть пару из конфига
```

### Лимит на устройство

**Симптом.** Рабочий сервер в Нидерландах (дата-центр Cloudflare AMS), один бесплатный аккаунт, через WARP — часть трафика Xray, около 35 новых соединений в секунду. Пользователи видели долгие TLS-рукопожатия и таймауты сайтов.

**Где терялось время.** Не в TLS, а в установке TCP. Через WARP висело ~2100 сокетов в `SYN-SENT`, больше тысячи из них — дольше минуты; из ~1150 SYN в секунду, уходивших в туннель, ~995 были повторами. Из 742 соединений Xray через WARP за 20 секунд 384 не открылись вовсе (`i/o timeout` после всех повторов, через 81 с), открывшиеся ждали ответа на SYN 0,4–1,4 с вместо единиц миллисекунд. Когда соединение всё же устанавливалось, TLS занимал столько же, сколько напрямую, 20–100 мс.

**Что исключено:**

- сам сервер: conntrack занят на 14%, процессор на 29%, потерь на интерфейсе нет; напрямую с того же сервера — 10 соединений из 10
- туннель: пинг через него 1–5 мс без потерь — теряется только TCP
- сайты: отказывал даже собственный адрес Cloudflare `1.1.1.1`
- площадка: тестовый сервер без пользователей в той же AMS — 10 из 10 за 3–7 мс

**Что пробовали и что не помогло:**

| Попытка | Результат |
|---|---|
| смена endpoint (`vps-warp rotate`) | около двух минут почти без отказов (26 из 534 соединений за 20 с), через три минуты снова ~1250 сокетов в `SYN-SENT` и прежние отказы |
| ключ WARP+ на том же аккаунте, сброс сессии | статус аккаунта `unlimited`, но картина та же: 1900–2600 сокетов в `SYN-SENT`, за минуту 1443 отказа по таймауту на 2372 соединения |
| ключ WARP+ на новом аккаунте, новая пара порт → endpoint, полный перезапуск интерфейса | `cdn-cgi/trace` показал `warp=plus`; через 3–10 минут 1600–2550 сокетов в `SYN-SENT`, за минуту 956–1256 отказов по таймауту на 2094–2541 соединение |

Ставка на «WARP+ быстрее» не сработала: платный аккаунт упирается в тот же лимит новых соединений, что и бесплатный, и за десять минут не «разогнался».

**Что помогло — второй аккаунт.** Новый бесплатный аккаунт на том же сервере, с тем же адресом выхода, в те же минуты. Четыре сайта, по 10 попыток соединиться с таймаутом 3 с:

|---|---|---|---|
| 1 | тот же, что у основного | 1–4 из 10 | 10 из 10, соединение за 1–11 мс |
| 2 | тот же | 0–1 из 10 | 10 из 10 |
| 3 | другой | 0–2 из 10 | 10 из 10 |

Вывод: ограничение стоит на устройство, то есть на аккаунт WARP, а не на адрес сервера, адрес выхода или машину Cloudflare.

**Итог на рабочем сервере — `--accounts 4`, четыре бесплатных аккаунта:**

Четыре аккаунта держали эту картину и через 20 минут, и после перехода на 5.1.

## Почему нужен нестрогий rp_filter

Туннель асимметричен by design: помеченные пакеты Xray уходят через `warp` (таблица 51820), а дефолтный маршрут сервера остаётся на основном интерфейсе. Расшифрованные ответы возвращаются на `warp` **без метки** — правило `fwmark 255` не срабатывает, лукап уходит в main table, упирается в дефолт через основной NIC, входящий интерфейс не совпадает. Строгий rp_filter такой пакет отбрасывает.

Симптом коварный: `wg show` показывает свежий handshake, `vps-warp` пишет `ACTIVE`, а трафика через туннель нет.

`wg-quick` эту ситуацию не закрывает. Его `sysctl net.ipv4.conf.all.src_valid_mark=1` живёт внутри `add_default()`, а `add_route()` попадает туда только при `Table = auto` или пустом `Table`. Интерфейсы vps-warp поднимаются с `Table = off`, маршрутов `wg-quick` не ставит вовсе, и `src_valid_mark` не выставляется никогда.

### Почему это не решается силами Xray

Xray умеет отключать `rp_filter` сам, но делает это только в `proxy/wireguard/tun_linux.go` — на kernel-TUN пути **встроенного** WireGuard-протокола. То есть срабатывает лишь при outbound/inbound с `"protocol": "wireguard"`, и внутри контейнера с read-only `/proc/sys` падает (`failed to disable ipv4 rp_filter for all: read-only file system`).

При нашей схеме Xray этот код не выполняет вообще: туннель ядерный, Xray ходит в него обычным `freedom` + `sockopt.mark`. Отсюда два следствия:

- **`privileged: true` для этой схемы не нужен.** Достаточно `NET_ADMIN` в docker-compose ноды — `SO_MARK` требует `CAP_NET_ADMIN`, не более
- **rp_filter обязан настроить кто-то на хосте**, потому что Xray про ядерный туннель ничего не знает. Этим и занимается скрипт

Если на ноде всё же используется встроенный WG-outbound Xray и он не стартует из-за rp_filter — помимо `privileged: true` есть вариант мягче: `"noKernelTun": true` в settings, откат на userspace-стек gVisor, которому привилегии не нужны. Ценой производительности.

Выбран loose (`=2`), а не `0`: он по-прежнему отбрасывает мартиан и немаршрутизируемые источники, разрешая только асимметричный путь. Скрипт трогает **только** значение `1` — если вы осознанно поставили `0`, оно останется.

## Удаление

```bash
vps-warp uninstall
```

Снимет сервисы всех аккаунтов, удалит правила и маршруты IPv4 и IPv6, правила MSS, погасит интерфейсы, уберёт sysctl-файлы и почистит все данные. Пакет `wireguard` остаётся установленным — при желании снесите руками.
